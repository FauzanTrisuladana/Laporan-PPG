\section{Tujuan Praktikum}
\begin{enumerate}
  \item Mampu memahami konsep persistensi data dan manajemen status permainan pada Unreal Engine.
  \item Mampu membuat dan mengimplementasikan \textit{Game Instance} sebagai pengelola data global yang bertahan lintas level permainan.
  \item Mampu merancang dan mengonfigurasi sistem \textit{Save Game} untuk menyimpan serta memuat progres permainan ke media penyimpanan lokal.
  \item Mampu menerapkan \textit{Blueprint Interface} untuk komunikasi dan pertukaran data antar-aktor secara modular dan \textit{decoupled}.
  \item Mampu mengintegrasikan mekanisme \textit{checkpoint} untuk menyimpan dan memulihkan posisi transformasi karakter pemain.
  \item Mampu menguji dan memvalidasi keberhasilan persistensi data permainan secara menyeluruh melalui simulasi \textit{Play-in-Editor} (PIE).
\end{enumerate}

\section{Dokumentasi Praktikum}

\par Bagian dokumentasi ini menyajikan rangkaian tahapan teknis yang saya laksanakan selama sesi Praktikum Pengembangan Game Pertemuan 5 dengan topik \textit{Game Instance \& Save Game} pada Unreal Engine 5. Pembahasan mencakup perancangan \textit{Structure} \texttt{S\_PlayerState} dan kelas \texttt{BP\_SaveGame}, konfigurasi kelas pengelola persisten \texttt{BP\_GameInstance} pada \textit{Project Settings}, implementasi komunikasi modular melalui \textit{Blueprint Interface} \texttt{BPI\_SaveData}, penyusunan alur komputasi penyimpanan dan pemuatan data di memori serta disk lokal, integrasi restorasi posisi karakter pada \texttt{BP\_ThirdPersonCharacter}, pembuatan aktor pemicu \texttt{BP\_CheckPoint}, hingga pengujian simulasi \textit{Play-in-Editor} (PIE) untuk memvalidasi keberhasilan persistensi posisi pemain antarsesi.

\subsection{Perancangan Structure dan BP\_SaveGame}

\par Pada tahapan awal praktikum, fokus pengembangan saya arahkan pada penyusunan fondasi arsitektur data yang akan disimpan ke dalam media penyimpanan disk. Dalam Unreal Engine, proses serialisasi data ke berkas lokal dengan format \texttt{.sav} dikelola melalui kelas khusus bernama \textit{SaveGame}. Oleh karena itu, saya mengawali langkah praktikum dengan menciptakan kelas dasar simpanan tersebut serta menyusun aset \textit{Structure} untuk merangkum atribut \textit{Transform} pemain secara terstruktur.

Pada jendela dialog \textit{Pick Parent Class}, saya memperluas kategori \textit{All Classes} dan mengetikkan kata kunci pencarian \texttt{save} pada bilah pencarian. Dari hasil daftar kelas yang ditampilkan, saya memilih kelas bawaan mesin \textit{SaveGame} sebagai \textit{parent class}. Pemilihan kelas ini sangat esensial karena mesin Unreal Engine telah menyediakan fungsi bawaan serialisasi data tingkat rendah pada kelas \textit{SaveGame} untuk menulis dan membaca status variabel secara efisien ke media penyimpanan fisik.

\subsection{Konfigurasi Blueprint Game Instance dan Project Settings}

\par Komponen penting berikutnya dalam arsitektur persistensi Unreal Engine adalah \textit{GameInstance}. Berbeda dengan aktor di level atau kelas \textit{GameMode} yang akan direset dan dihancurkan setiap kali transisi level berlangsung, objek \textit{GameInstance} diinisiasi satu kali saat aplikasi game pertama kali diluncurkan dan terus hidup di memori RAM hingga proses permainan ditutup secara penuh. Oleh karena itu, saya mengimplementasikan \textit{GameInstance} kustom sebagai jembatan perantara antara aktor aktif di dalam level dengan berkas simpanan fisik di disk.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{resource/Dokumentasi/8.png}
  \caption{Pemilihan Parent Class GameInstance pada Dialog Pick Parent Class}
  \label{fig:gameinstance-pick-parent}
\end{figure}

\par Berdasarkan Gambar \ref{fig:gameinstance-pick-parent}, saya kembali membuka jendela dialog \textit{Pick Parent Class} melalui \textit{Content Drawer}. Pada bilah pencarian \textit{parent class}, saya mengetikkan kata kunci \texttt{game ins} dan memilih kelas \textit{GameInstance}. Kelas dasar ini menyediakan fungsionalitas penanganan siklus hidup tingkat aplikasi yang melampaui siklus hidup \textit{level} permainan, menjadikannya lokasi ideal untuk menaruh data global sesi permainan.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{resource/Dokumentasi/9.png}

\par Berdasarkan Gambar \ref{fig:gameinstance-asset-created}, berkas \texttt{BP\_GameInstance} terbentuk pada direktori \texttt{Content > Blueprints}. Kelas ini mengelola logika penyimpanan dan pemuatan data yang dapat diakses oleh seluruh aktor memanfaatkan node \texttt{Get Game Instance}.

\begin{figure}[H]
  \centering

\par Agar mesin Unreal Engine mengenali dan menjalankan kelas \texttt{BP\_GameInstance} saat simulasi dimulai, saya harus mendaftarkannya pada konfigurasi tingkat proyek. Sebagaimana ditunjukkan pada Gambar \ref{fig:project-settings-gameinstance}, saya membuka menu \textit{Edit > Project Settings}, lalu menavigasi ke bagian \textit{Project > Maps \& Modes}. Pada kategori \textit{Game Instance} di bagian bawah panel konfigurasi, saya mengubah properti \textit{Game Instance Class} dari kelas bawaan menjadi \texttt{BP\_GameInstance}. Perubahan ini tersimpan secara otomatis pada berkas konfigurasi \texttt{DefaultEngine.ini}, sehingga mesin akan selalu menginstansiasi kelas ini setiap kali sesi permainan dieksekusi.

Pada kolom \textit{Default Value} untuk variabel \texttt{SlotName}, saya mengisi nilai \texttt{1}. \subsection{Perancangan Blueprint Interface BPI\_SaveData}

\par Untuk membangun komunikasi yang bersih dan modular antara berbagai aktor dalam permainan dengan \textit{GameInstance}, saya menerapkan pola perancangan menggunakan \textit{Blueprint Interface}. Penerapan ini menghilangkan kebutuhan \textit{hard casting} ke kelas \texttt{BP\_GameInstance}, sehingga mencegah terjadinya \textit{circular dependency} dan menjaga performa kompilasi proyek tetap optimal.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{resource/Dokumentasi/13.png}

\par Berdasarkan Gambar \ref{fig:bpi-create-menu}, saya mengeklik kanan pada area kerja \textit{Content Drawer} di dalam folder \texttt{Content > Blueprints}, lalu mengarahkan kursor ke menu \textit{Blueprint} dan memilih opsi \textit{Blueprint Interface}. Berbeda dengan kelas Blueprint biasa, \textit{Blueprint Interface} hanya memuat deklarasi nama fungsi beserta parameter \textit{Inputs} dan \textit{Outputs} tanpa menyertakan blok kode implementasi di dalamnya.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{resource/Dokumentasi/14.png}

\par Gambar \ref{fig:bpi-savedata-created} menampilkan aset \textit{Blueprint Interface} baru yang berhasil dibuat dan saya beri nama \texttt{BPI\_SaveData} dengan prefiks standar \texttt{BPI\_}. Aset ini disiapkan sebagai kontrak komunikasi universal untuk seluruh operasi penyimpanan dan pengambilan status permainan.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{resource/Dokumentasi/15.png}

Melalui panel \textit{Details} pada kategori \textit{Inputs}, saya menambahkan satu parameter input bernama \texttt{Async} bertipe data \textit{Boolean}. Parameter ini berfungsi sebagai sakelar penentu apakah operasi pemuatan data dari disk akan dilakukan secara asinkron pada \textit{background thread} atau secara sinkron pada \textit{main game thread}.

\begin{figure}[H]

  \includegraphics[width=0.8\textwidth]{resource/Dokumentasi/16.png}

Serupa dengan fungsi pemuatan, fungsi ini juga saya konfigurasikan dengan parameter input tunggal berupa \texttt{Async} bertipe data \textit{Boolean}. Parameter ini digunakan untuk menentukan mode penulisan berkas simpanan ke penyimpanan disk lokal.

Pada panel \textit{Details} bagian \textit{Outputs}, saya menambahkan parameter \texttt{S\_PlayerState} dengan tipe data \textit{Structure} \texttt{S\_PlayerState}. Melalui fungsi ini, seluruh aktor dalam level permainan dapat memperoleh data transformasi pemain tanpa harus mengetahui detail implementasi internal \textit{GameInstance}.

\begin{figure}[H]

\section{Hasil Akhir}

\par Berdasarkan seluruh rangkaian perancangan, implementasi, dan pengujian teknis yang telah saya laksanakan pada Praktikum Pengembangan Game Pertemuan 5 mengenai materi \textit{Game Instance \& Save Game}, berikut adalah kesimpulan dan analisis komprehensif atas pencapaian hasil praktikum:
\begin{enumerate}[label=\alph*.]
  \item \textbf{Keberhasilan Implementasi Arsitektur Game Instance dan Save Game:} Saya telah berhasil merancang dan mengintegrasikan dua pilar persistensi data Unreal Engine 5, yaitu kelas berbasis \textit{SaveGame} (\texttt{BP\_SaveGame}) sebagai penampung serialisasi data non-volatil pada sistem berkas lokal (\texttt{.sav}), serta kelas \textit{GameInstance} (\texttt{BP\_GameInstance}) sebagai pengelola data volatil global di memori RAM yang memiliki siklus hidup persisten melampaui siklus hidup level individual. Konfigurasi \textit{Game Instance Class} pada \textit{Project Settings Maps \& Modes} terbukti berhasil mengaktifkan kelas pengelola kustom ini sejak detik pertama aplikasi dijalankan.
  \item \textbf{Efektivitas Komunikasi Modular melalui Blueprint Interface:} Penerapan \textit{Blueprint Interface} \texttt{BPI\_SaveData} terbukti efektif dalam membangun arsitektur sistem permainan yang bersifat \textit{decoupled}. Karakter pemain dan checkpoint dapat berkomunikasi dua arah dengan \textit{GameInstance} tanpa memerlukan \textit{hard casting}. Hal ini meningkatkan modularitas sistem sekaligus mencegah dependensi sirkular antar-aset.
  \item \textbf{Optimasi Kinerja Penyimpanan Data Asinkron:} Implementasi parameter \texttt{Async} pada sistem penyimpanan membuktikan pentingnya pemilihan metode I/O dalam pengembangan game. Penggunaan node \texttt{Async Save Game to Slot} pada pemicu checkpoint memungkinkan penulisan data ke disk diproses di \textit{background thread} tanpa mengganggu \textit{main game thread}, sehingga mencegah terjadinya lonjakan \textit{frame time} maupun \textit{hitch} pada simulasi.
  \item \textbf{Presisi Mekanisme Restorasi Koordinat Spasial Karakter:} Pengujian restorasi koordinat pada siklus hidup \texttt{Event BeginPlay} di dalam \texttt{BP\_ThirdPersonCharacter} menunjukkan akurasi posisi yang sangat presisi. Logika validasi vektor berhasil membedakan inisiasi permainan awal pada titik \textit{PlayerStart} dengan sesi lanjutan yang merestorasi posisi karakter langsung ke koordinat checkpoint via node \texttt{Set Actor Location}.
  \item \textbf{Validasi Integritas Sistem melalui Simulasi Play-in-Editor (PIE):} Seluruh siklus persistensi data terbukti berhasil secara empiris melalui pengujian dua sesi berurutan. Karakter yang melintasi volume \textit{Box Collision} \texttt{BP\_CheckPoint} berhasil memicu perekaman posisi melalui pengaman \texttt{Do Once}. Pada peluncuran simulasi berikutnya, karakter langsung dimunculkan pada posisi checkpoint yang tersimpan. Pengujian ini memastikan tidak ada data yang hilang maupun kesalahan \textit{null reference} selama runtime.
